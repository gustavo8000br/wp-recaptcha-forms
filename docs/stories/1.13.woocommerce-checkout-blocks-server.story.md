# Story 1.13 — Checkout WooCommerce Blocks: validação server-side (W-2)

## Status
Draft

## Priority
P1 — Cobertura de formulários (W-2 de 3, depende de W-1)

## Story
**Como** dono de loja com checkout em Blocks (default em Woo recente),
**quero** que a Store API rejeite submissões sem verificação válida,
**para que** o checkout em Blocks tenha a mesma proteção do checkout clássico, testável sem navegador.

## Backlog / Arquitetura
- B-12 (checkout Blocks, servidor), R-02
- Arquitetura v1 §8.3 (servidor), §8.4 (W-2 testável via REST)
- Arquitetura v1.1 §8.1 — **o campo `cstate` precisa entrar no schema junto do `token`, senão diverge do clássico**

## Acceptance Criteria

1. Campo de extensão registrado via `woocommerce_store_api_register_endpoint_data` no schema `CheckoutSchema::IDENTIFIER`, namespace `wp-recaptcha-forms`, com **dois** campos: `token` e `cstate` (não só `token` — resolve a lacuna apontada na v1.1 §8.1).
2. Validação em `woocommerce_store_api_checkout_update_order_from_request`: lê `$request['extensions']['wp-recaptcha-forms']['token']` e `['cstate']`, chama **a mesma** `Gate::assess()` com `form_id='woocommerce_checkout'` e `action='wrf_woocommerce_checkout'` (idênticos à Story 1.12/W-1).
3. Bloqueio lança `RouteException('wrf_blocked', $verdict->message(), 400)` — a Store API converte em resposta 400 exibida como aviso na UI do Blocks.
4. Testável isoladamente por requisição REST direta à Store API, com e sem `extensions.wp-recaptcha-forms.token`/`cstate` — sem navegador, sem React.
5. Só é registrada se Woo >= 8.3 e a interface do Blocks existir (guard da Story 1.11).
6. Testes automatizados cobrindo: requisição com token válido passa; sem token e `cstate=''` → 400; sem token e `cstate=no-script` com política allow → passa; com política block → 400 com mensagem distinta (§1.7 da v1.1).
