# Story 1.31 — Transporte: WP-Cron semanal, jitter, envio e tratamento de falha

## Status
Draft

## Priority
P1 — sem transporte a feature não faz nada. Última das stories de núcleo.

## Story
**Como** autor do plugin,
**quero** que o envelope seja enviado uma vez por semana, fora do caminho de qualquer submissão, com jitter, timeout curto e desistência limpa em caso de falha,
**para que** a minha API nunca derrube um checkout do operador e para que uma indisponibilidade minha nunca vire problema dele.

## Backlog / Arquitetura
- `docs/telemetry-design.md` §6.1 (quando: WP-Cron semanal, nunca no request de formulário; jitter derivado do `instance_id`; `wp_doing_cron()` real), §6.2 (como: `wp_remote_post` com `timeout=5`, `redirection=0`, `blocking=true`, `sslverify=true`, UA sem `site_url()`), §6.3 (falha: fire-and-forget + 1 retentativa; 2xx/4xx/5xx/429; nunca admin notice; nunca desliga proteção; zerar contadores só pós-2xx, sem fila)
- Decisão do dono T-6 (semanal com jitter derivado do `instance_id`)
- Depende de 1.27 (`instance_id` estável), 1.28 (`Counters::reset()`), 1.29 (`Envelope::build()`), 1.26 (`telemetry.seq`/`last_sent`/`last_status`)

## Acceptance Criteria

1. **Agendamento**: ao `grant()` (Story 1.27), agenda um evento cron `wp_recaptcha_forms_telemetry_send`. Ao `revoke()`, `wp_clear_scheduled_hook()` do mesmo. Schedule customizado `wp_recaptcha_forms_weekly` (7 dias) registrado via `cron_schedules` (WP não traz `weekly` garantido em todas as versões do range de compat).
2. **Jitter**: o primeiro agendamento é para `time() + $offset`, com
   `$offset = hexdec( substr( $instance_id, 0, 4 ) ) % ( 7 * DAY_IN_SECONDS )`.
   Determinístico por instalação, uniformemente espalhado. Sem estado extra.
3. **Guarda de contexto**: o handler só roda sob `wp_doing_cron()` **real** (não `wp_doing_ajax()`). Funciona igual em site com `DISABLE_WP_CRON` + cron de sistema. Nenhum envio jamais parte de um request de formulário — teste que o handler não é registrado em nenhum hook de submissão e que chamar `assess()` nunca dispara rede de telemetria.
4. **Guarda de estado**: o handler aborta silenciosamente (sem reagendar fora do ciclo) se `Options::telemetry_enabled()` for `false` — cobre a corrida "cron disparou depois do opt-out".
5. **Envio** (`Telemetry\Transport::send( array $envelope ): array`), com `wp_remote_post( $endpoint, [...] )`:
   - `timeout => 5`, `redirection => 0`, `blocking => true`, `sslverify => true` (nunca desligar, nem "temporariamente" — comentário no código);
   - headers: `Content-Type: application/json`, `User-Agent: 'wp-recaptcha-forms/' . WRF_VERSION` (**sem `site_url()`**), `Idempotency-Key: <envelope_id>`;
   - body: `wp_json_encode( $envelope )`;
   - endpoint em constante única `Telemetry\Endpoints::INGEST` (`https://telemetry.gustavomathias.dev/...` — valor exato confirmado com o dono; ver Dev Notes), no mesmo espírito de `Provider/Endpoints.php`.
6. **Tratamento de resposta**:
   | Situação | Comportamento |
   |---|---|
   | 2xx | `Counters::reset()`, `telemetry.seq += 1`, `telemetry.last_sent = time()`, `last_status = 'ok'` |
   | `WP_Error` / timeout / 5xx | agenda **uma** retentativa em +1 h com o **mesmo `envelope_id`**; `last_status='error'`; após a retentativa falhar, desiste e espera a janela semanal |
   | 429 | lê `Retry-After`, agenda retentativa para depois disso (uma só); sem retentativa antes |
   | 400 | **desiste, não retenta**; `last_status` = corpo (`schema_unknown`/`pii_suspected`/`payload_too_large`); se `pii_suspected`, `error_log` sob `WP_DEBUG` (bug meu) |
   | API fora por semanas | nada acontece — sem fila, sem acúmulo em opção, sem crescer nada no banco |
7. **`envelope_id` reusado no retry**: o `envelope_id` do envelope que falhou é persistido (transiente curto ou campo em `telemetry`) e passado a `Envelope::build( $id )` na retentativa. Idempotência da API (§1.2) depende disso.
8. **Contadores zerados só pós-2xx e sem fila**: se o envio da semana falhou, os contadores da semana seguinte incluem a anterior e `event.window.from` (Story 1.29 AC 2) declara isso. Nunca zera antes do 2xx.
9. **Nunca admin notice** por falha de telemetria — teste que confirma que nenhum `add_action('admin_notices', ...)` é registrado pelo namespace de telemetria. Contraste deliberado com MISCONFIG (v1.1 §4.3).
10. **Nunca desliga a proteção** por falha de telemetria — o envio não cruza o `Gate` em ponto nenhum; teste que uma falha total de `Transport` deixa `assess()` intacto.
11. `last_status` é diagnóstico local (consumível pela tela na Story 1.32) — **nunca** vira notice.
12. Testes (com `FakeHttp`/filtro `pre_http_request`):
    - jitter determinístico para um `instance_id` fixo;
    - 200 → contadores zerados, `seq` +1, `last_sent` gravado;
    - 500 → uma retentativa agendada, mesmo `envelope_id`, contadores intactos;
    - 429 com `Retry-After: 3600` → retentativa agendada para +3600s;
    - 400 `pii_suspected` → sem retentativa, `last_status` gravado, linha em `error_log` sob `WP_DEBUG`;
    - opt-out no meio → `wp_clear_scheduled_hook` chamado, handler subsequente aborta;
    - handler não registrado em hook de submissão.

## Dev Notes
- **`Telemetry\Endpoints::INGEST` — valor exato é decisão do dono** (T-2 no design lista a política pública da API como pré-requisito de lançamento). `[AUTO-DECISION]` para a story: usar `https://telemetry.gustavomathias.dev/v1/ingest` como placeholder documentado, marcado com TODO rastreável, a confirmar antes do beta. Não bloqueia a implementação nem os testes (que usam `pre_http_request`).
- `blocking => true` de propósito (§6.3): `false` seria fire-and-forget puro mas impede saber se funcionou, e sem isso não há como decidir retry nem preencher `last_status`. Em cron, bloquear 5 s não custa a ninguém.
- Retentativa via `wp_schedule_single_event`, não loop com `sleep`.
- Este código vive sob o gate da Story 1.30 — `src/Telemetry/Transport.php` não pode conter `site_url`/`home_url`/`get_bloginfo`. O UA é `WRF_VERSION`, constante.
