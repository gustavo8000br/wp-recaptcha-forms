# Story 1.18 — Versionamento e pipeline de CI

## Status
InReview

## Priority
P2 — Qualidade e distribuição (gate de release)

## Story
**Como** mantenedor,
**quero** um esquema de versionamento adaptado ao contexto de plugin, com CI aplicando as regras automaticamente,
**para que** a versão nunca seja editada à mão e o CHANGELOG nunca fique desatualizado.

## Backlog / Arquitetura
- B-14, FR-14 (backlog §4, arquitetura v1 §11)

## Acceptance Criteria

1. Esquema `vMAJOR.MINOR.PATCH-HHHHHHH-stage` adotado, com as regras de bump da backlog §4 (MAJOR = quebra de compatibilidade de hook/filtro/helper público, mudança de formato de opção sem migração, elevação de piso PHP/WP, mudança de postura de segurança nomeada — ver Story 1.3 e 1.11 para os gatilhos específicos; MINOR = novo ponto de integração/opção retrocompatível; PATCH = correção de bug sem mudança de contrato).
2. Toda PR exige label `version:major|minor|patch|none` — gate falha sem label, sem default.
3. `bin/stamp-version.php` escreve, a partir da tag do git no release: header do plugin (`Version:` só `MAJOR.MINOR.PATCH`), `WP_RECAPTCHA_FORMS_VERSION`, `WP_RECAPTCHA_FORMS_BUILD`. Teste unitário afirma que os três batem entre si.
4. `CHANGELOG.md` obrigatório: toda mudança entra em `[Unreleased]`; o CI valida a presença de entrada em PRs que tocam `src/`, `assets/` ou `bin/`.
5. CI executa: `phpcs` (WPCS), `phpunit`, `bin/check-boundary.sh` (Story 1.2), `bin/i18n-e2e.sh` (Story 1.20), `bin/i18n-progress.php --check` (Story 1.20), validação de `.mo`/bundle Blocks vs. build (Stories 1.14/1.21).
6. Matriz de teste em CI: PHP 7.4 / 8.1 / 8.3 × WP 6.0 / WP latest (unitário), mais uma célula adicional WP 6.6 ou 6.7 (resolve R-11 — faixa onde `.l10n.php`/`_load_textdomain_just_in_time` mudam de comportamento). Eixo de integração com Woo latest só.
7. `bin/build-zip.sh` gera o artefato distribuível excluindo `.git`, `docs/` (exceto o necessário), `tests/`, `node_modules`.

## Dev Agent Record

### O que faltava e foi feito

O `release.yml` já rodava a suíte, mas só na tag. Gate que só existe no release troca o
custo de "PR vermelho" pelo de "release abortada". O `ci.yml` roda em todo push e PR para
`main`:

| Job | O que roda |
|---|---|
| `test` (× PHP 7.4, 8.1, 8.3) | `composer test`, `composer check:boundary`, `composer i18n:e2e` |
| `lint` | `composer lint` |
| `i18n` | tabela de progresso em dia, três idiomas mantidos a 100%, `.po`/`.mo` consistentes |
| `pr-hygiene` | label `version:*` única e obrigatória, `MAJOR-JUSTIFICATIVA:` quando MAJOR, `CHANGELOG.md` quando o código muda |

### Decisões que valem registro

**A label de versão não é derivada da mensagem de commit.** O AC 2 diz "sem default", e é
o certo: escolher entre MINOR e PATCH é juízo humano sobre raio de alcance, e um prefixo
`feat:`/`fix:` não sabe se a mudança quebra contrato público. O job falha também quando há
**mais de uma** label de nível — duas labels são tão indefinidas quanto nenhuma.

**A exigência de CHANGELOG é condicional.** Só vale quando o diff toca
`src/`, `assets/`, `bin/`, `wp-recaptcha-forms.php` ou `uninstall.php`. A regra existe pelo
histórico do usuário, não para punir quem corrige um typo na documentação.

**O `.mo` é reconstruído e comparado**, não só conferido quanto à existência. Um `.mo`
desatualizado no commit é um idioma que aparece 100% na tabela de progresso e não traduz
nada no site — falha silenciosa, que é o tipo que este projeto vem tratando como
prioritária.

### AC 6 — entregue pela metade, declaradamente

Eixo de PHP (7.4 / 8.1 / 8.3): entregue, e as três versões foram executadas a mão nesta
rodada. **Eixo de WordPress (6.0 / latest / 6.6-6.7): não entregue.** Exigiria um WordPress
e um banco por célula, e a suíte unitária foi desenhada para não carregar WordPress — a
matriz de WP só faria sentido para os testes de integração, hoje três arquivos rodados por
WP-CLI. **R-11 continua aberto.** Registrado em `docs/compatibility-matrix.md` §3 e §4.

### AC 7 — atendido sem criar `bin/build-zip.sh`

O `release.yml` já monta o zip com `rsync --exclude-from=.distignore` e já confere que o
arquivo principal está lá e que o header bate com a tag. Um `bin/build-zip.sh` separado
seria uma segunda definição da mesma lista de exclusões, com prazo para divergir da
primeira. O `.distignore` é a fonte única.

### Verificação

O YAML foi validado com parser (`yaml.safe_load`) e a lógica de shell dos jobs `i18n` e
`pr-hygiene` foi executada localmente em container antes do commit — os três `.mo`
reconstroem byte a byte idênticos aos commitados.
