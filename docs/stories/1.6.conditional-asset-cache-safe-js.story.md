# Story 1.6 — Carregamento condicional de asset + JS cache-safe

## Status
InReview

## Priority
P0 — Fundação

## Story
**Como** plugin,
**quero** carregar o script do Google só nas páginas com formulário protegido, e obter o token em tempo de submit (nunca no HTML),
**para que** o produto seja imune ao bug clássico de token cacheado e não penalize performance de páginas sem formulário.

## Backlog / Arquitetura
- B-07, FR-07 (arquitetura v1 §6, D-06/R-01)
- Arquitetura v1.1 §1 (BL-01 — sinal `cstate`), §2.5 (carregamento sob demanda por consentimento — só o contrato aqui; `ConsentGate` é a Story 1.16)

## Acceptance Criteria

1. `AssetManager` só enfileira `api.js`/script do v2 em páginas onde ao menos uma integração ativa está presente (via Registry). Home sem formulário não carrega o script.
2. `FieldRenderer` imprime **apenas** hidden fields vazios no HTML: `wrf_token`, `wrf_action`, `wrf_cstate`. Nenhum valor com validade, nenhum dado específico de usuário — o HTML é idêntico e cacheável para todo visitante (invariante A3).
3. JS de frontend (`frontend.js`) implementa o intercepto de submit da arquitetura v1.1 §1.3: `waitForGrecaptcha()` com timeout de 4s (filtrável via `wrf.loadTimeout`), `grecaptcha.execute()`, preenchimento dos hidden fields, `requestSubmit()` preservando o `submitter` (fallback `submit()` só se `requestSubmit` indisponível).
4. `wrf_cstate` é escrito com um dos valores do vocabulário fechado (`no-script`, `consent-pending`, `exec-error`) conforme a falha do cliente; vazio no caminho feliz. **O formulário sempre é submetido** — o `.then()` final é um `finally` lógico, com ou sem token.
5. Aviso amigável (`wrf-notice`, `role="status" aria-live="polite"`) inserido dinamicamente pelo JS quando `cstate` é setado, com texto vindo de `wp_localize_script` (traduzido — cobre-se pelo gate de pseudo-locale da Story 1.20).
6. Scripts marcados com `data-cfasync="false"`, `data-no-optimize="1"`, `data-no-defer="1"`, `data-nowprocket` via `script_loader_tag`, para sobreviver a "Delay JS" de plugins de cache.
7. Listener de submit registrado em `document` na fase de captura, não no `<form>` — sobrevive a formulários re-renderizados por outros scripts.
8. v2 checkbox: callback `expired-callback` registrado para limpar o campo quando a resposta expira.
9. Teste manual roteirizado documentado em `docs/release-checklist.md` (S-05 da v1 §6.6): cache de página real, esperar 5 min, submeter, inspecionar o HTML cacheado (`value=""`, nenhum nonce, nenhum dado de usuário).

## Dev Agent Record

**Decisões que a story não fixava:**

1. **O critério de "página com formulário protegido" é o campo ter sido impresso.**
   `FieldRenderer` avisa o `AssetManager` no momento em que imprime; não existe lista de
   páginas para manter nem heurística a errar. Os handles são registrados no
   `wp_enqueue_scripts`/`login_enqueue_scripts` e só enfileirados sob demanda.
2. **`login_enqueue_scripts` além de `wp_enqueue_scripts`.** `wp-login.php` não dispara o
   segundo, e sem isso o formulário de login teria campo e nenhum script — todo login viraria
   token vazio.
3. **O script do provedor é registrado com `ver = null`.** Acrescentar `?ver=` a uma URL de
   terceiro invalidaria o cache de navegador dele a cada release nossa, sem ganho.
4. **Fallback de `submitter` sem `requestSubmit`.** Em navegador antigo, o botão clicado é
   recriado como hidden antes do `submit()`, senão o formulário com dois botões perde qual foi
   clicado — exatamente o caso do carrinho do WooCommerce.
5. **O contrato JS de consentimento (`window.wpRecaptchaForms.grantConsent`) já existe aqui**,
   ainda que o `ConsentGate` seja a Story 1.16. Sem ele o `cstate=consent-pending` nunca poderia
   ser produzido, e a Story 1.3 já o trata. O carregamento sob demanda do script fica para lá.

**Verificado no ambiente Docker, no HTML servido de verdade:**
- Página **sem** formulário protegido (home): **zero** ocorrências de `recaptcha` no HTML.
- Página **com** formulário protegido (login, via fixture temporário): os três hidden fields
  saem **vazios** (`wrf_token`, `wrf_action`, `wrf_cstate`), e os dois scripts saem com
  `data-cfasync="false" data-no-optimize="1" data-no-defer="1" data-nowprocket`.
- **Invariante A3 medido, não presumido:** duas requisições anônimas ao mesmo formulário
  produzem um bloco `.wrf-field` byte a byte idêntico, e não há nonce dentro dele.
- Dados de `wp_localize_script` conferidos: só site key (pública), versão, timeout e a
  mensagem traduzida. Nada específico de usuário.
- **Kill switch ponta a ponta:** com `WRF_DISABLE`, o login vem com zero campos `wrf_` e zero
  scripts do Google. Fecha a última asserção da Story 1.1 AC7, que dependia desta story.
- `node --check` nos dois bundles; `php -l`, `phpunit` (71 testes) e os 4 gates de fronteira
  verdes.
- O fixture temporário de integração foi **removido**, e a remoção foi provada: o login voltou
  a sair com zero campos `wrf_` e o diretório `mu-plugins` está vazio.
