# Story 1.2 — Fronteira de verificação do Google (Provider/Transport)

## Status
InReview

## Priority
P0 — Fundação

## Story
**Como** mantenedor do plugin,
**quero** que todo conhecimento sobre o endpoint, vocabulário de erro e formato de resposta do Google fique isolado num único diretório testável sem rede,
**para que** trocar de endpoint (recaptcha.net, futura migração Enterprise) seja reescrever uma classe, não caçar strings pelo código.

## Backlog / Arquitetura
- B-02, FR-02 (arquitetura v1 §4)
- R-04 (isolamento da fronteira HTTP)

## Acceptance Criteria

1. `ProviderInterface` implementado com `verify()`, `version()`, `script_url()`; `verify()` nunca lança exceção — falha sempre vira `ProviderResponse`.
2. `VerificationRequest` e `ProviderResponse` são imutáveis. `ProviderResponse::debug_codes()` existe e só é consumido em log/admin, nunca em lógica de decisão.
3. `TransportInterface` com `WpHttpTransport` (embrulha `wp_remote_post`, timeout 5s filtrável via `wp_recaptcha_forms_request_timeout`, `redirection => 0`, `sslverify => true`) e `FakeTransport` para testes (injeção direta, sem depender do hook global `pre_http_request`).
4. `src/Provider/Endpoints.php` é o único arquivo do repositório com a string `recaptcha/api`. Filtro `wp_recaptcha_forms_endpoint( $url, $which )` documentado e testado (cobre o caso `recaptcha.net`).
5. Gate de CI `bin/check-boundary.sh` implementado com as duas verificações de grep da arquitetura §4.5, **sem a armadilha de `pipefail`** (resolve OB-06 — script deve funcionar corretamente sob `set -o pipefail` ou documentar explicitamente por que não usa).
6. Nenhuma classe/arquivo fora de `src/Provider/` referencia `error-codes` do Google (`invalid-input-`, `timeout-or-duplicate`) — verificado pelo gate de CI.
7. Testes unitários com `FakeTransport` cobrindo: sucesso, timeout, HTTP 5xx, HTTP 429, corpo não-JSON, corpo vazio — sem rede real.

## Dev Agent Record

**Desvios de implementação, com razão:**

1. **`ProviderInterface` ganhou um quarto método, `token_field()`.** No v2 o campo de token é
   gerado pelo script do provedor com um nome que é vocabulário DELE. Se o coletor único da
   Story 1.3 conhecesse esse nome, a fronteira A2 já teria vazado — e é justamente BL-06.
   O provider responde qual campo ler; o coletor pergunta. O gate de CI passa a proibir esse
   nome fora de `src/Provider/`, o que só é possível por causa deste método.
2. **`FailureClass` foi criada aqui**, não na Story 1.3. Ela mora em `src/Provider/` pela
   arquitetura §10 e `ProviderResponse::failure()` a referencia — não dava para adiar sem
   deixar a assinatura mentindo. A Story 1.3 consome e testa.
3. **`TransportResult::json()`** decodifica no transporte, não no provider. Corpo vazio e
   corpo não-JSON viram `null` em vez de exceção, e a tradução de `null` para INFRA continua
   sendo do provider. É o que permite testar as linhas "corpo não-JSON" e "corpo vazio" da
   matriz nesta story, antes de os providers existirem.
4. **`check-boundary.sh` roda COM `set -euo pipefail` de propósito** e testa o conteúdo de uma
   variável, não o código de saída de um pipeline (OB-06). O padrão original
   `! grep -rl ... | grep -v ...` passa por acidente sob `pipefail`.

**Verificado:**
- `php /tmp/phpunit.phar` no container: **OK, 9 testes, 21 asserções**, sem rede.
- `bash bin/check-boundary.sh` → aprovado no código real; e **reprovado com exit 1** quando
  plantei um arquivo em `src/Gate/` com a URL do provedor e com `invalid-input-secret`.
  O gate morde de verdade.

## Dev Notes
- Arquitetura v1 §4 inteira é a especificação desta story.
- `AbstractSiteverifyProvider`, `SiteverifyV3`, `SiteverifyV2` e a tabela de classificação (§5/§4.2 da v1.1) são da **Story 1.4** — esta story entrega só a fronteira de transporte e o contrato, não a implementação v3/v2.
- OB-06 (qa-plan-review-v1 §5): o `check-boundary.sh` precisa ser robusto a `pipefail` — não repetir o padrão `grep -rl ... | grep -v ...` sem verificar o código de saída corretamente.
