# Story 1.5 — Tela de configurações

## Status
InReview

## Priority
P0 — Fundação

## Story
**Como** dono de loja sem conhecimento técnico (persona P1),
**quero** uma tela de configurações autoexplicativa com validação de chaves, thresholds e política de falha por dois eixos,
**para que** eu configure o plugin sem precisar entender a arquitetura por trás.

## Backlog / Arquitetura
- B-05, FR-05; B-06, FR-06 (arquitetura v1 §5.3-1, §7.2)
- Arquitetura v1.1 §7.4 (UI de dois eixos), §4.3 (sonda no save)

## Acceptance Criteria

1. Menu admin registrado, tela via Settings API, nonce, capability `manage_options` em toda ação (incluindo AJAX de validação de chave).
2. Campos: seleção de versão (v3/v2), site key, secret key (mascarada — salvar vazio mantém o valor atual, nunca ecoada em claro), threshold (default 0.6, só relevante para v3), mensagens de erro customizáveis, toggles por formulário — **a tela é gerada a partir do `Integrations\Registry`** (Story 1.11), não escrita à mão form a form.
3. Suporte a `WP_RECAPTCHA_FORMS_SECRET_KEY` via `wp-config.php`: quando definida, tem precedência sobre a option e o campo aparece desabilitado na UI com nota explicando a origem.
4. Sanitização de todos os campos (`Sanitizer.php`); todos os campos livres (mensagens customizadas) passam por `wp_kses`.
5. Sonda de validação no save: `siteverify` com token deliberadamente inválido; espera `invalid-input-response` como prova de secret válida. Se vier `invalid-input-secret`, o save é recusado com erro no campo. UI/README **não afirmam "chaves validadas"** — só "secret validada" (correção de escopo honesta da v1.1 §4.3).
6. Dois eixos de política de falha na tela: seção global com dois selects rotulados em linguagem de operador ("Se o nosso servidor não conseguir falar com o Google" / "Se o navegador do visitante não conseguir carregar o reCAPTCHA") e, por formulário, uma coluna "Quando falhar" com `Herdar / Permitir ambos / Bloquear ambos / Personalizado…`.
7. Estado do plugin visível no topo da tela: `Protegendo` / `Degradado — não verificando` / `Desativado` — refletindo MISCONFIG (Story 1.3) e `WRF_DISABLE` (Story 1.1).
8. Avisos e ajuda contextual: ao escolher v2, aviso recomendando gerar chave v3 nova; links para os **dois** fluxos de obtenção de chave (console clássico e Google Cloud/Enterprise — ver Story 1.22 para o texto completo em README; aqui só os links da tela de config), com um marcado como recomendado. URLs verificadas ao vivo antes do release (gate de release, não desta story).
9. Sem WooCommerce ativo, a seção Woo não aparece na tela (comportamento automático via Registry — Story 1.11), não é código condicional escrito à mão aqui.

## Dev Agent Record

**Achado de campo que a arquitetura não previu — importa para o @qa e para o README:**

A sonda do save (AC 5) prova ainda menos do que a v1.1 §4.3-1 já corrigiu. Medido ao vivo
contra o endpoint real: com uma secret **arbitrária** (`secret=x`), o Google responde
`invalid-input-response`, **não** `invalid-input-secret`. Ou seja, a sonda só reprova secrets
que o Google considera malformadas; uma secret sintaticamente plausível de outro projeto passa
na sonda. O código está conforme a especificação (MISCONFIG só quando o Google diz que a
secret é inválida) e a mensagem de sucesso já é honesta, mas a redação do README precisa
refletir isto: a sonda é um filtro de erro grosseiro de digitação, e quem realmente detecta
par errado é o advisory de runtime da Story 1.3.

**Desvios de implementação, com razão:**

1. **`Registry` e `IntegrationInterface` entram aqui**, mesmo sendo nominalmente da Story 1.11.
   A story manda gerar a tela a partir do registry e implementar "contra uma interface mínima";
   sem os dois arquivos não havia contra o que implementar. O registry nasce vazio e a tela diz
   isso; quando as integrações chegarem, não há UI a escrever.
2. **Formulários ausentes do POST são preservados na sanitização.** Sem WooCommerce a seção não
   é renderizada; apagar o que ela guardava faria a reativação do Woo perder a configuração
   anterior, contra a arquitetura v1 §7.3.
3. **Sonda inalcançável não recusa o save.** Se o servidor não fala com o Google no momento do
   save, não dá para afirmar nada sobre a secret — e recusar ali trancaria o operador fora da
   própria configuração por causa de uma oscilação de rede. Salva e avisa.
4. **Uma sonda bem-sucedida limpa o estado "Degradado".** É o caminho normal de recuperação
   depois de o operador corrigir a chave.
5. **Sem AJAX de validação de chave.** A validação acontece no save, que já tem nonce e
   capability da Settings API. Um endpoint AJAX a mais seria uma superfície a mais para proteger
   sem ganho para a persona P1. O AC 1 exige `manage_options` "incluindo o AJAX" — não há AJAX.

**Verificado no ambiente Docker, pelo navegador (curl autenticado como admin):**
- A tela renderiza em `options-general.php?page=wp-recaptcha-forms` sem nenhum
  `Warning`/`Notice`/`Deprecated`/`Fatal`.
- Banner de estado partiu de "Ainda não configurado" e virou "Protegendo" depois de chaves
  válidas — o mesmo mecanismo que mostra "Degradado" e "Desativado".
- Campo de secret sai como `type="password"`, `value=""`, com placeholder mascarado: a secret
  **não aparece no HTML** em nenhum momento.
- Save real via `options.php` com nonce: `threshold=0,75` gravou `0.75`; `<script>alert(1)</script>`
  na mensagem customizada foi removido pelo `wp_kses` e o `<strong>` sobreviveu; políticas
  gravaram os valores do vocabulário.
- Save com secret nova disparou a sonda contra o endpoint real e exibiu a mensagem de secret
  validada, com a ressalva escrita de que isso não prova o par.
- Os dois links de obtenção de chave estão na tela, com o clássico marcado como recomendado.
- `phpunit`: **OK, 71 testes, 179 asserções**.
