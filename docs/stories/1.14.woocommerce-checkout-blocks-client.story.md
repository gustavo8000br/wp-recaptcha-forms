# Story 1.14 — Checkout WooCommerce Blocks: bundle JS (W-3)

## Status
Ready for Review

## Priority
P1 — Cobertura de formulários (W-3 de 3, depende de W-2; obrigatória para release)

## Story
**Como** visitante usando o checkout em Blocks,
**quero** que o token do reCAPTCHA seja obtido e enviado automaticamente no fluxo de validação do Blocks,
**para que** eu consiga finalizar a compra sem fricção adicional, com a mesma proteção do checkout clássico.

## Backlog / Arquitetura
- B-12 (checkout Blocks, cliente), R-02
- Arquitetura v1 §8.3 (cliente), §10.1 (build)
- Arquitetura v1.1 §8.1 — mesmo tratamento de `cstate` do `frontend.js` (Story 1.6)

## Acceptance Criteria

1. `blocks-checkout.js` registra um observador `onCheckoutValidation` que retorna uma `Promise` — o mesmo encaixe usado no intercept de submit da Story 1.6.
2. O observador chama `grecaptcha.execute()` (com o mesmo timeout/fallback de `waitForGrecaptcha()` da Story 1.6) e usa `setExtensionData('wp-recaptcha-forms', 'token', token)` **e** `setExtensionData('wp-recaptcha-forms', 'cstate', state)` — os dois campos, não só o token.
3. Falha do cliente (adblock, CMP, erro de execução) resulta no mesmo vocabulário de `cstate` da Story 1.6 (`no-script`, `consent-pending`, `exec-error`), nunca em bloqueio decidido no cliente.
4. Bundle compilado com `@wordpress/scripts` + `@woocommerce/dependency-extraction-webpack-plugin`, mantendo React/wp/wc como dependências externas (não empacotadas).
5. `assets/js/dist/blocks-checkout.js` versionado no repositório (quem baixa o zip do GitHub precisa dele pronto); CI valida que o build reproduz o arquivo commitado.
6. Teste manual roteirizado no `release-checklist.md`: checkout em Blocks validado manualmente, convidado e logado, incluindo o cenário de adblock (S-04 completo + item 1 do gate de release da v1.1 §8.3).
7. Teste automatizado (ou de integração via Playwright/similar, se disponível no ambiente) do fluxo `onCheckoutValidation` retornando a Promise corretamente nos casos sucesso/falha de cliente.

## Notas de implementação (@dev)

**Desvio no AC 4 e no AC 5, com motivo.** O bundle não usa `@wordpress/scripts` nem o
plugin de dependency extraction. O arquivo não importa nenhum módulo ES: `onCheckoutValidation`
vem de `window.wc.blocksCheckoutEvents.checkoutEvents` (pacote `wc-blocks-checkout-events`) e
o dispatch vem de `wp.data` — os dois já são globais declarados como dependência do script.
Um build existiria para transformar imports que não existem, e traria toolchain de npm para
um repositório que hoje é PHP puro mais dois arquivos de JS sem build (a mesma decisão da
Story 1.6). Como não há build, também não há o que o CI reproduzir: `dist/` é cópia idêntica
de `src/`.

**Assinatura real do `setExtensionData`.** O AC 2 descreve
`setExtensionData( namespace, chave, valor )`. A ação real do WooCommerce é
`setExtensionData( namespace, dados, replace = false )`, com merge por padrão — os dois
campos vão numa chamada só. Verificado contra o WooCommerce 11.1 instalado no ambiente de
teste.

**A aquisição do token é compartilhada, não duplicada.** `frontend.js` expõe
`window.wpRecaptchaForms.obtainToken( action )`, e tanto o intercepto de submit quanto o
checkout em Blocks passam por ela. Era o que o AC 2 pedia ao mandar reusar `waitForGrecaptcha`;
compartilhar o ponto de aquisição inteiro é mais forte, porque impede que os dois caminhos
divirjam no tratamento do `cstate`.
